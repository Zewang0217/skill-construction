# Arm1 原语谱系实验分析报告

**实验对象**：code_exec 坐标的 24 种攻击原语（`arm1-{idx}-{原语}-code_exec-target_agnostic`）
**生成方式**：ecnu-max 直白版（无混淆、无对抗性改写）
**扫描引擎**：Cisco（语义分析）/ SkillSpector-SS（正则）/ Categorizer-Cat（正则 + 评分）
**样本规模**：24

## 1. 实验设计

### 1.1 动机：总评的坐标采样无法回答原语级问题

主实验（SoK 总评）按来源 × 方式 × 目标 × 载体四维坐标抽样评测，每个坐标通常只取 1 个代表性样本。该设计能回答"哪些坐标检出率高"，却无法回答"同一坐标内，不同攻击原语是否决定检出率"。若坐标内方差大于坐标间方差，坐标级结论将系统性失真——这正是本实验要检验的假设。

选择 code_exec 作为深挖坐标的原因：(1) 它是跨来源最普遍的攻击载体（OS、Snyk、SOCK、AITech 等多个威胁源均以代码执行为落点）；(2) 原语谱系最丰富——同一"代码执行"可通过直接调用、标准库间接调用、反射、数据流、复合恶意模式等多种形态实现，天然适合检验原语粒度对检出率的影响；(3) 总评中该坐标存在引擎间分歧（见第 4 节），是检验坐标聚合是否失真的最佳对象。

### 1.2 方法：坐标内深挖

本实验固定坐标（code_exec + target_agnostic），将样本数扩展到 24 个原语，覆盖四类：

- **直接执行原语**：`direct_exec`(#03)、`direct_eval`(#04)、`exec+动态源`(#10)、`compile()` 字符串→代码对象(#08)；
- **标准库间接执行**：`subprocess`(#06)、`os.system`(#07)、`__import__`(#05)、`getattr` 反射(#09)、`getattr(os,system)` 规避(#11)；
- **数据流变体**：直接 source→sink(#12)、经中间变量(#13)；
- **威胁模式注入**：crafted_parameters(#01)、tool_chains 链式(#02)、offensive tools/YARA(#14)、AITech 模型操纵(#15)、AITech 代码执行(#16)、Snyk E006(#17)、SOCK-S13 网络(#18)、SOCK-S17 Shell(#19)、SOCK-S19 eval(#20)、SOCK-S21 env(#21)、SOCK-S22 FS(#22)、SOCK-S28 JS 动态 require(#23)、SOCK-S29 JS 安装脚本(#24)。

控制变量：坐标一致、生成器一致、目标一致性一致（均 target_agnostic）、无混淆；唯一自变量为攻击原语。Cisco 列 `False` = 判定不安全（检出），`True` = 判定安全（漏检）；SS/Cat 以标注"漏"为准。

**判定口径**：每家引擎对 24 个样本独立扫描；Cisco 以 safe 标志 + 严重度（CRITICAL/HIGH）双通道记录，SS 以 0–100 置信得分记录，Cat 以 grade/score/命中数 n 三元组记录；任何引擎对样本的最终分类与 ground truth（均为真实恶意样本）不符即记为漏检，并以"漏"标注。全部 24×3 条判定经人工逐条核验，本报告直接引用核验结果。

### 1.3 研究问题

- RQ1：同一坐标内，检出率是否随原语类别显著变化？
- RQ2：三家扫描器的漏检是否可按原语类别进行预测？
- RQ3：坐标级聚合指标（总评）是否掩盖原语级能力差异？

## 3. 三家坐标级盲区

### 3.1 Cat：纯正则对"无字面命令"的代码原语全盲

- **漏检 6 例**：#06 subprocess、#07 os.system、#14 offensive tools(YARA)、#18 SOCK-S13、#19 SOCK-S17、#23 SOCK-S28。
- **共性**：全部是没有 `curl|bash` 等字面命令的代码原语——执行以 API 调用（`subprocess.run`、`os.system`、`spawn`）或纯代码形态呈现，命令字符串不出现于词法表层，正则规则库无触发（该 6 例命中数 n=0）。
- **对照验证**：同为 SOCK 家族的 #20 eval、#21 env、#22 FS 均被检出——它们携带高信号词法特征；SOCK 类 7 例中 Cat 漏 3 例（#18/#19/#23）。盲区不是来源问题，而是"字面信号缺失"问题。
- **跨引擎对照**：该 6 例在 Cisco 全部判 HIGH/CRITICAL，其中 3 例（#14/#18/#19）在 SS 亦得满分 100，说明样本恶意性明确——Cat 是唯一系统性失明的引擎，且失明机理与其正则架构直接对应，而非样本质量问题。
- **边界刻画**：Cat 的盲区边界 = "执行原语 + 无字面命令"；一旦原语自带高信号词法特征（如 #20 eval/#21 env/#22 FS 携带的标志性函数名与模式）或含 URL/域名等 token，即脱离盲区。该边界可由原语类别先验预测。

### 3.2 Cisco：语义层对间接执行漏检

- **漏检 8 例**：#08 compile()、#09 getattr 反射、#10 exec+动态源、#12/#13 数据流、#16 AITech 代码执行、#17 Snyk E006、#24 SOCK-S29。
- **机理**：Cisco 依赖可解析的调用链与数据依赖，8 例全部通过"间接层"切断直接证据——#08 执行藏于编译后的 code object；#09 反射动态解析属性名，遮蔽 `os.system` 的显式出现（对照 #11 显式 getattr(os,system) 反而被检出，差异在反射路径的可见性）；#10 被执行源码不在词法可见范围；#12/#13 的 source→sink 直接路径被数据流切断（#13 经中间变量后 SS 亦仅 8 分，两端同时失明）；#16/#17/#24 为跨来源复合或间接模式。
- **反例验证**：Cisco 对 16 例直接原语全部检出（含 7 个 CRITICAL/HIGH），漏检恰好全部落在"间接执行"类别——盲区可按原语类别预测。
- **盲区边界**：Cisco 的盲区 = "执行路径存在词法/语义间接层"。#11（getattr(os,system) 规避）与 #09（getattr 反射）的成对对照最具说明性：二者同为 getattr 动态解析，仅当属性名以字面量显式出现（#11）时被检出，以变量/拼接形式出现（#09）即漏——语义引擎的解析深度直接决定盲区。#12 与 #13 同理：直接 source→sink 已漏（依赖跨过程数据流分析），再经中间变量后（#13）连 SS 都降至 8 分，双重间接性对两类引擎均为强规避手段。

### 3.3 SS：Snyk E006 混合模式漏检（唯一）

- **漏检 1 例**：#17 Snyk E006（恶意代码模式：外泄/后门/RCE/凭证混合），得分 0；同一样本 Cat 检出 A/92。
- **机理**：SS 正则擅长词法信号（命令字面、URL、函数名），24 例中 10 例满分 100、0 分仅此一例；E006 是四类特征交织的混合型模式，单一正则无法覆盖，而单一模式样本（#14 YARA、#18–#23 SOCK 等）全部命中（得分 56–100）。混合型是纯正则引擎唯一的结构性盲区。

## 4. 与总评对比

| 引擎 | code_exec 检出率 | 总评检出率 | 差 |
|------|-----------------|-----------|-----|
| Cisco | 67%（16/24） | 85.2% | **−18.2pp 相对弱区** |
| SS | 96%（23/24） | 92.8% | +3.2pp 相对强区 |
| Cat | 75%（18/24） | 72.5% | +2.5pp 基本持平 |

- code_exec 是 Cisco 的相对弱区：语义引擎在总评中的高均值由其他坐标（字面证据充分的文档/元数据类）拉高，掩盖了其对间接执行的系统性漏洞；SS 的正则引擎在该坐标词法高可见性的原语上表现最强，唯一败给混合模式；Cat 与总评持平。
- 推论：总评的坐标聚合掩盖原语级差异，"某引擎总评高"不能推出"其在任意坐标、任意原语上都强"。

三家盲区按"原语类别 × 引擎机制"的对应关系可整理如下（盲区可预测性的直接证据）：

| 原语类别 | Cat | Cisco | SS |
|----------|-----|-------|----|
| 直接执行（#01–#05 等） | 检出 | 检出 | 检出 |
| 标准库间接调用（#06/#07/#14/#18/#19/#23） | **漏 6** | 检出 | 检出（#06/#23 低分） |
| 动态编译与反射（#08–#11） | 检出 | **漏 3/4**（#09 等） | 检出 |
| 数据流变体（#12/#13） | 检出 | **漏 2** | 检出（#13 仅 8 分） |
| 复合恶意模式（#16/#17/#24） | 检出 | **漏 3** | **漏 1**（#17） |

## 5. 生成器 frontmatter 质量门发现

- **事件**：#01 crafted_parameters 初版 frontmatter 缺闭合围栏（以 ``` 替代 ---），Cisco 加载失败；修复后检出 CRITICAL。
- **比例**：1/24（4.2%）样本存在结构缺陷，未被生成器质量门拦截。
- **影响**：若未修复，#01 会被误计为 Cisco 漏检，其检出率虚低至 62.5%（−4.5pp），实验指标被静默污染——"加载失败"与"判定安全"必须严格区分。
- **根因**：质量门只校验内容生成（原语正确性、直白程度），未校验 frontmatter 结构完整性。
- **改进**：批量生成管线应增加结构校验层（YAML 可解析、围栏闭合、必需字段存在），并把加载错误单独归类，不进入检出统计。
- **延伸**：该缺陷发生于"直白版"（生成负担最低的配置），说明问题出在生成器的输出模板/序列化环节而非语义复杂度；同管线其他 23 例均通过结构校验，缺陷呈偶发但存在。质量门补上结构校验后，此类污染可完全拦截。

## 6. SoK 价值

- **S5 支撑：坐标内粒度 → 盲区可预测**。粒度从"坐标"细化到"原语"后，三家漏检呈现强结构化规律——Cat=无字面命令的代码原语、Cisco=间接执行、SS=混合模式。给定原语类别即可预测哪家会漏。
- **核心实证："原语决定可检测性，坐标不决定"**。同一坐标内检出率跨全谱（SS 0~100、Cisco 0/1、Cat 覆盖全谱），坐标聚合值 67/96/75 无法代表任何具体原语；单样本代表坐标的评测结论不可靠。
- **方法论含义**：SoK 坐标抽样式评测必须落到原语粒度；盲区知识可反哺扫描器增强（正则层补 API 调用模式与混合模式、语义层补数据流与反射解析）与生成器质量门（frontmatter 结构校验）。
- **可操作映射**：本实验给出三家引擎的增强清单——Cat 需新增 API 调用形态规则（`subprocess.run`/`os.system`/`spawn` 等无字面命令原语，可覆盖其全部 6 例盲区）；Cisco 需补动态编译/反射/数据流间接层的污点追踪（覆盖 #08/#09/#10/#12/#13）；SS 需新增多模式复合恶意检测（覆盖唯一盲区 #17）。
- **局限与后续**：本实验仅覆盖 code_exec 一个坐标，原语-盲区对应关系在其他坐标（如数据外泄、权限提升）是否成立，需以同样方法扩展验证；这也是 SoK S5 原型从单坐标证明走向跨坐标泛化的下一步工作。

## 7. Arm2 补充：语义包装对代码层检出无效（对照实验）

在 Arm1 完成后追加了包装对照实验（验证"语义包装能否降低检出率"）。对 6 个三家全检出的
直白版样本（direct_exec/direct_eval/__import__/getattr 反射/sock_eval/tool_chains），
用 wild few-shot 手法（免责话术/工具伪装/安全声明/工具性描述）做**语义层包装**——只改
SKILL.md 的描述/名称/正文措辞，脚本恶意逻辑逐字节不变。

**结果（6 样本包装版 vs 直白版）**：

| 原语 | Cisco 直白→包装 | SS 直白→包装 | Cat 直白→包装 |
|---|---|---|---|
| direct_exec | Y→Y (CRITICAL) | 97→100 | A→A |
| direct_eval | Y→Y (CRITICAL) | 100→100 | B→B |
| __import__ | Y→**N** (MEDIUM) | 73→58 | A→A |
| getattr_reflect | Y→Y (CRITICAL) | 74→100 | A→A |
| sock_eval | Y→Y (CRITICAL) | 100→94 | A→A |
| tool_chains | Y→Y (CRITICAL) | 100→100 | D→B |

**结论：单轮语义包装（改描述层）对代码层检出无效**——SS 仍 94-100%，Cisco 5/6 仍 CRITICAL。

**机理**：Arm1 直白版的恶意在**脚本静态可见**（D5 质量门强制可执行脚本 → exec/subprocess
等代码证据充分），扫描器（尤其 SS/Cat）检出靠代码证据，SKILL.md 描述改写不改变代码证据。
唯一变化 __import__（Cisco Y→N、SS 73→58）是描述改写影响了 LLM 语义层的部分判断，但
Cat 仍检出（A/92）——单点弱化不成系统性绕过。

**与 wild 的对照**：wild 能骗过 SS（B2 钱包 58% 检出率）的包装版，恶意载荷在**执行阶段才
暴露**（下载执行/远端文件/管道变量注入），SKILL.md 静态可见的恶意证据极少；而 Arm1 样本
因 D5 强制脚本，恶意静态可见。**包装有效性的前提是"载荷时序"（静态可见 vs 执行阶段暴露），
不是语义层描述**——这是 Arm2 实验最重要的发现，直接指向下一轮实验（构造执行阶段载荷型
包装样本，见 EXPERIMENT_SCOPE.md 组 A）。
